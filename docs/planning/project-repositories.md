# 下一版本：项目关联多个 GitHub 仓库与 Organization

2026-10-06 用户新增需求，安排在当前 Preview 修复和验收完成后。
本文件记录下一版本范围；该功能尚未实现，当前没有迁移或数据变更。

用户随后明确：下一版本还需要多人共用账本，以及成员角色权限控制。
因此这是团队账本功能版本，不再仅是组织归属标签。

一个记账项目应能显式关联多个已授权 GitHub 仓库，并支持 Organization
关联。当前项目表、REST 创建入参和 Web 选择器均为单仓库；历史支出
已经引用稳定的 project ID，改为独立关联表后可保留历史支出与报表归属。
个人账户下的多仓库项目与组织归属属于中等功能改动。

GitHub App 已能发现用户可访问的多个 installation 下的仓库，包括组织
安装；下一版需要保留 GitHub 返回的稳定组织 ID/type 元数据，提供组织
筛选和仓库多选。维持已授权仓库范围，不自动安装所有仓库或纳入未来新增
仓库。项目关联变化使用版本条件和原子权限检查，逐仓库处理授权撤销，
历史账目与原 projectIds API-key 范围保持稳定。

实施需要新增仓库关联表及旧映射回填、REST/OpenAPI 契约、Web 多选与
关联列表、预算和配额计费、真实本地 D1 迁移验收。报表继续按 project
聚合，不能连接多仓库表后重复累计支出。不能直接修改已发布的旧 migration。

## 多人账本与角色

新增稳定的账本/workspace 身份、成员表及邀请流程。个人账本继续保留，
成员必须显式加入团队账本；GitHub 组织成员资格不会自动授予财务数据
访问权。每条项目、分类、支出、报表查询、CSV 和自动化密钥都绑定同一
账本边界，服务端逐请求核对权限，不能只隐藏前端按钮。

以下四个角色作为下一版设计起点：

| 能力 | Owner | Admin | Editor | Viewer |
| --- | --- | --- | --- | --- |
| 查看项目、支出、报表和 CSV | 是 | 是 | 是 | 是 |
| 新增、编辑、删除账目 | 是 | 是 | 是 | 否 |
| 管理项目、分类和仓库关联 | 是 | 是 | 否 | 否 |
| 邀请、移除 Editor/Viewer | 是 | 是 | 否 | 否 |
| 授予/撤销 Admin | 是 | 否 | 否 | 否 |
| 账本所有权、关闭账本、订阅付款 | 是 | 否 | 否 | 否 |

保留至少一个 Owner，禁止 Admin 自行成为 Owner。邀请需单次接受、期限
与撤销控制；移除成员或降低角色后，后续请求立即失去相应权限。历史审计
同时记录所属账本和真实操作成员，不能把所有成员动作都记成账本 Owner。
API-key 权限与当前角色、账本及项目范围取交集，不得借密钥恢复已撤销
权限或越过 Shared Pool 限制。所有成员操作共享账本的配额和模型预算，
不得通过换成员绕过限额；订阅归属与多人收费规则需在实施前具体定义。

## 实施顺序与验证

先完成账本隔离、角色和邀请，再接入多仓库及 Organization，最后补 Web
账本切换、成员管理和完整验收。迁移保留现有个人账目、project ID 和原
API-key 范围；不自动转移现有数据，也不将支出复制到每个关联仓库。
验证覆盖不同账本的读写隔离、每个角色的服务端拒绝、撤销权限、邀请
复用/过期、并发关联变更，以及历史金额和报表不变。该功能尚未开发，
不能用本轮单人 Preview 验收作为团队权限已经通过的证据。

仍需在下一版开始时确定跨组织项目、一仓库是否可关联多个项目、部分
仓库失权策略及团队订阅规则。按用户要求，在当前版本完成后独立实施。
